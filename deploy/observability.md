# Observability setup and evidence

## What is implemented

- `/api/v1/health`: backend liveness only (used by Docker). It deliberately stays healthy during a simulator failure.
- `/api/v1/status`: validated instance + simulation-metrics probes, UTC check time, HTTP 503 for stale/unavailable data, and HTTP 200 after recovery. Simulator health alone bypasses fault injection and is insufficient. This is not a guarantee that every simulator endpoint works.
- `/api/v1/observability/metrics`: bearer-token protected, disabled without `OBSERVABILITY_TOKEN`. Process-lifetime request/error/upstream/stale/command/stream/degradation/recovery counters, route-template counts, and average/p50/p95/p99 over the most recent 1000 completed non-stream requests. Zero samples means no latency evidence yet. Counters reset on restart. Run one Uvicorn worker (the default); these are not multiprocess aggregates.
- JSON stdout logs: UTC timestamp, generated request ID, route template, response status, duration, simulator failures and health transitions. Bodies, headers, query strings, identifiers in URLs, and validation input values are not logged by this instrumentation. `X-Request-ID` is returned for correlation; this is not distributed tracing.
- Backend Docker logs rotate at 10 MB with three files. Uvicorn raw access logs are disabled in the image to avoid duplicating requests and logging query strings.
- Frontend: live status panel, automatic refresh with one bounded retry, explicit unknown/stale states, simulated service level/unmet demand/allocation failures. Previous health is never presented as current after connection failure. No automatic simulator writes or write retries.
- Existing dashboard partial-result degradation remains intact and is measured.

Recommendation engine metrics are **not implemented**: the requested base branch has no engine. Prediction error/confidence, decision frequency, shortage alerts and model fallback must be instrumented when that code is integrated. Do not substitute simulator service level for model accuracy. No application database exists, so no database-health claim is made.

## 1. Deploy the code

Merge through the team's normal reviewed deployment path. This feature branch is based on `feature/frontend-backend-api`, which predates the main-branch deployment workflow; it does not replace or modify the existing main deployment pipeline. Nothing here auto-pushes or deploys the branch.

On the VPS, add a randomly generated monitoring token to the real Compose `.env` as `OBSERVABILITY_TOKEN`. Keep it out of Git and frontend environment variables. Generate it locally with a password manager (at least 32 random bytes). Recreate the backend using your existing deployment process so it receives the new environment. Keep `SIMULATOR_WRITES_ENABLED=false` for the publicly accessible backend.

Verify backend `/api/v1/health` and `/api/v1/status`, and the frontend `/api/backend/v1/status`. A paused simulator should still yield healthy status. A real schema/connection error should not be hidden to make the check green.

## 3. Install the supplied FSIRP plugin

The plugin uses only Python's standard library and reads the backend over VPS loopback. It adds application measurements without installing a second APM exporter or a monitoring database.

1. Copy `deploy/site24x7/fsirp/fsirp.py` into `/opt/site24x7/monagent/plugins/fsirp/fsirp.py` on the VPS (verify your agent's installation path first).
2. Beside that script, create a file named `token` containing exactly the same token as `OBSERVABILITY_TOKEN`. Allow only root and the agent's actual service account to read it; do not make it world-readable. Do not place it in a command-line argument.
3. Run `python3 /opt/site24x7/monagent/plugins/fsirp/fsirp.py` as the agent account. It should print JSON with latency, counters, `dependency_healthy` and `simulation_data_fresh`. `status: 0` means collection failed, not healthy zero traffic.
4. Wait for agent discovery; confirm the FSIRP plugin monitor appears. Enable heartbeat alerts so stopped collection is visible.
5. Add charts for request/error counters, recent-window p95/p99, simulator errors/stale detections, dashboard degradation and recovery. Counter differences divided by scrape elapsed seconds give request/error rates; discard intervals across uptime resets. Do not alert on a lifetime error counter being greater than zero forever.
6. Alert on `dependency_healthy < 1` or `simulation_data_fresh < 1`, and enable recovery notifications. Simulation outcome fields are `-1` (unknown, not actual fuel quantities) while freshness is zero. Exclude those samples from business charts. `requests_per_second_since_start` is a process-lifetime average, not an instantaneous rate.

The plugin intentionally does not send tokens, simulator bodies, route IDs or raw logs. Installation activates external telemetry transfer; approve this with your team before running the agent.

## 4. Add external checks

In **Add Monitor → REST API**, create separate monitors:

- Backend liveness: `https://hackathon.bebsapati.com/api/v1/health`, expected HTTP 200 and JSON `status` = `ok`.
- Simulator integration: `https://hackathon.bebsapati.com/api/v1/status`, expected HTTP 200 and JSON `status` = `healthy`.
- End-to-end: your actual Vercel origin + `/api/backend/v1/status`, same assertions.
- Frontend: use a Website monitor for the actual Vercel homepage.

Start with a 1-minute poll and email notifications. Configure dependency failures/recovery to notify promptly, subject to account confirmation/alert settings. Short faults may fall between polls. External response time is probe latency, not the distribution of all application requests. Keep simulator port 8000 and `/admin` private.

## 6. Failure and recovery demonstration

On an authorized local/demo simulator only:

1. Record a healthy panel and `/api/v1/status` response.
2. Using the existing private simulator admin console, inject `unavailable` for 180 wall-clock seconds (longer than polling/confirmation delays). Do not reset shared state or expose admin routes.
3. Show liveness remains 200 while dependency status becomes 503, the UI says degraded, logs record `simulator_failure` / `health_transition`, and Site24x7 alerts. Dashboard snapshot should retain valid partial resources and mark unavailable ones explicitly.
4. After the fault expires, show fresh REST data, healthy UI/status, recovery log/counter, and recovery notification.
5. Repeat with `stale_data`: upstream may return HTTP 200, but our dependency check must return 503 and UI must mark stale. A paused tick by itself is not stale.
6. Capture screenshots and actual detection/recovery times. Tests also cover malformed responses and timeouts. Stream opening failures, interruptions and invalid events have separate counters; stream lifetimes are excluded from request latency percentiles. Full frontend SSE integration is not supplied by this branch; the health panel uses REST polling.

## 7. Load test

Run against a local or explicitly approved demo deployment, without active fault injection. The dashboard snapshot fans out to 12 simulator requests, so begin with the supplied 2 users, 30 seconds and a one-second pause. Do not run on an unrelated production host.

Windows PowerShell, repository root, Docker available:

```powershell
New-Item -ItemType Directory -Force ./load-tests/results | Out-Null
docker run --rm -v "${PWD}/load-tests:/scripts" grafana/k6 run --summary-export=/scripts/results/summary.json /scripts/dashboard.js
```

Default backend target is `http://host.docker.internal:8001`. To test an authorized different origin, pass `-e BASE_URL=YOUR_APPROVED_BACKEND_ORIGIN` before `grafana/k6`. This script targets the backend path, not the frontend rewrite. Never include a secret in that URL.

Capture the runner output and Site24x7 resource graphs for the same time window. Record endpoint, commit, host size, simulator state, workload, completed requests, throughput, errors/check failures, average/p50/p95/p99 and resource peaks. Proposed starting thresholds are <1% HTTP errors, >99% complete/fresh snapshots and p95 <3 seconds; they are test objectives, not guaranteed results. Failure is evidence to investigate, not a reason to silently weaken thresholds.

Run the load generator off the VPS for final evidence. Local Docker-on-one-host results are only a smoke test, not VPS capacity measurements. Generated results are ignored by Git; curate redacted evidence deliberately.
